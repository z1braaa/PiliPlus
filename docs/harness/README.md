# 需求实施与验证 Harness

本目录把[后续需求](../requirements/README.md)转换为可复核的开发工作。它记录证据、约束、验收和状态。[并发 CDN V2](../parallel-cdn-playback-v2.md)是已实现的基线；P0 起播改进已在工作分支实施并按[验收矩阵](validation.md)记录测试范围，真实海外网络收益仍待测。直播增强尚未实施。

| 文件 | 用途 |
| --- | --- |
| [需求追踪表](traceability.md) | 每个稳定 ID 的阶段、来源、验证方法与当前状态 |
| [证据规则](evidence.md) | BTR、项目源码、官方直播静态资源的证据等级及重新核对要求 |
| [验收矩阵](validation.md) | 测试场景、测量口径、性能提案与结果记录模板 |
| [设计决策](decisions.md) | 已确定约束、待决事项和改变决定所需的证据 |

## 执行顺序

1. **确定范围**：选取追踪表中的一个或一组 ID，记录基线提交、目标平台、受影响模块和不涉及的模块。新增范围先补 ID、验收和来源。
2. **核验证据**：复核对应代码、BTR 固定版本或官方直播当前页面。静态请求线索升格为可调用接口前，确认方法、参数、登录/权限、返回、错误及版本；涉及用户支出或账号状态的流程需要授权测试和服务端结果核对。
3. **实施隔离**：点播传输、直播界面与未来直播网络加速分别验收。BTR 的浏览器 MSE 与 Electron 注入思路需要适配 Flutter / media_kit / mpv。增强界面与直播播放器、基本弹幕连接保持分离。
4. **分层验证**：先运行与改动相应的协议/组件测试，再做原生播放或界面检查，最后按目标网络和平台进行用户可感知的验收。执行结果记录为通过、失败、未运行或不适用；不以静态分析或模拟结果代替实际播放收益。
5. **交付核对**：将需求 ID、变更、证据链接、测试环境、结果和未解决限制写入验证记录。只有验收达到定义标准，才把追踪状态改为“已验证”。

## 阶段交付

| 阶段 | 进入前需确认 | 可供审查的交付 |
| --- | --- | --- |
| P0：点播起播 | V2 基线；目标网络样本缺失时明确性能验收待完成；先建立 `NET-01` 可取得的时间线 | `NET-01`～`07` 的分阶段耗时、协议正确性、真实 A/B 数据及未达目标的原因 |
| P1：持续播放 | P0 不破坏稳态播放；中断与过期场景可复现 | `NET-08`～`12` 的恢复、会话隔离和脱敏诊断记录 |
| P2：可选调度 | 固定手动配置可作为对照；明确地区规则是否保持 | `NET-13`～`16` 逐项独立结果，含性能收益和额外流量/内存成本 |
| L0：直播基准 | 当前官方网页与 PC 版本、代表房间/账号条件 | 模块入口、事件/API 证据等级、原生或 H5 选型，以及尚未验证的权限/交易清单 |
| L1：直播基础 | L0 对基础布局与消息的证据足够；V2 直播播放基线可复现 | 默认关闭的增强开关、直播不中断切换、SC 删除/过期和基础回归 |
| L2～L4：互动对齐 | 对应模块的请求协议、权限、价格/状态来源已核实 | 礼物/粉丝团、SC/大航海、高级互动逐模块验收；每项标明原生、混合、外部跳转或尚未完成 |

直播网络加速另立需求与验收；不能用直播界面增强的验收代替流媒体传输测量。

## 状态词

| 状态 | 含义 |
| --- | --- |
| 规划中 | 已写需求；未交付该项功能 |
| 待核实 | 关键网页/协议/平台基准仍缺证据，不能据此实现完整流程或宣称等量 |
| 实现中 | 源码已着手修改，完成标准仍未满足 |
| 已实现待验 | 行为已进入代码，但指定验收尚未跑完 |
| 已验证 | 指定验收通过并有可追溯记录；性能结论限于被测环境 |
| 暂缓 | 需求保留，需记录原因和恢复条件 |

当前状态以[需求追踪表](traceability.md)为准，区分回环测试、原生播放、GUI 和目标网络实测。V2 的历史测试结果只在其原文档中记录，不能自动算作 `NET-*` 的验证。
