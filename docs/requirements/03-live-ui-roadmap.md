# PiliPlus 直播观看端：功能差距与更新大纲

调研日期：2026-09-23（Asia/Singapore）；2026-09-24 迁入项目文档。本文件仅整理需求与方案，**没有修改业务源码、调用付费接口、登录账号或实施这些功能**。本地代码基线为 `15656d2182ef6c976a534c02f20820abc9e14ce7`。

## 1. 目标与本次验证范围

目标是让 PiliPlus 直播观看端逐步具备官方网页与官方 Windows PC 客户端的观看、互动、礼物和粉丝身份管理能力。“等量功能”需要形成逐项验收清单，不能用“加上一个礼物按钮”作为完成标准。

本次已核对：

- 本地直播页面、网络接口、弹幕连接、消息分发、SC、榜单、屏蔽、勋章墙等代码。
- 新增官方模块静态采集：13 份官方资源、42 项观察；已识别核心组件、H5 面板和请求线索，但未执行这些业务接口。详见[模块清单](research/04-official-live-module-inventory.md)。
- 官方网页直播间的匿名可见界面，以及官方帮助中心的礼物、粉丝团、大航海、醒目留言说明。动态帮助正文通过后台浏览器读取；单纯网页文本抓取返回空正文，不能据此判断功能不存在。
- **尚未实测最新官方 PC 客户端**，没有核验登录后的全部网页入口、限定账号权益和活动房间。因此“全部官方 PC 功能已列全”和“相关接口都能直接接入”均不能视为已证实。

首轮适配应以 macOS 桌面为主，随后逐项验证 Windows/Linux 与移动端布局及账号行为。这里的“PC 端”指观看客户端；开播推流、主播收益、公会管理等主播后台不属于观看端对齐范围。房管在观看页面可执行的管理操作，应单独列为有权限用户的扩展能力。

### 官方模块采集是新增功能的主要依据

礼物、背包、入团/勋章管理、SC 购买和大航海等新增能力，不能从 BTR 下载器中获得。后续需要独立采集并核对官方直播网页的模块、公开前端资源、请求线索与房间能力，再映射为 PiliPlus 原生组件和服务。PiliPlus 已有的播放、弹幕、SC 展示与勋章展示可复用；完整互动流程仍需自行实现。

主界面采用原生组件；若官方模块本身由独立 H5 面板承载，则比较原生重实现与嵌入官方面板的可行性。后者必须验证账号同步、宿主通信、操作确认、支付及结果回调，不能把仅能打开一个页面当作功能完成。两种实现分别记录完成度与限制。

具体模块来源和当前验证程度见 [官方直播模块采集与证据清单](research/04-official-live-module-inventory.md)。每个模块须区分页面入口已见、脚本请求线索已见、只读响应已核对，以及登录/权限/实际操作仍待核验。公开脚本静态出现一个接口，不足以将它标为可直接调用的稳定接口。

## 2. 先分清三个容易混淆的概念

- **粉丝团灯牌**：礼物或入团相关入口。匿名官方直播间的礼物栏中能够看到该名称。
- **粉丝勋章**：账号与主播的粉丝团身份，涉及持有、佩戴、等级、亲密度、点亮状态和权益。
- **大航海**：舰长、提督、总督等付费身份，具有有效期、续费及对应权益。

因此，“能看到弹幕旁的勋章”不等于“能加入粉丝团、佩戴勋章和完成点亮任务”；“能显示 SC”也不等于“能购买和发送 SC”。

官方当前粉丝团帮助已经描述“关注主播后，经粉丝团入口支付入团费用”的流程，任务和升级权益以房间粉丝团页面为准。其点亮说明与多年以前的攻略不同。**不要把旧攻略中的固定价格、天数、亲密度表或特定礼物名称直接写死到客户端**；入团方式、任务条件、期限、价格应以该账号和该房间当前服务端返回结果为准。[官方粉丝勋章帮助](https://link.bilibili.com/p/help/index#/audience-fans-medal)

## 4. 桌面直播间界面建议

推荐把桌面界面组织成“播放器主区 + 可调侧栏 + 下方互动区”。保持视频面积优先，所有低频入口按需展开。

```text
┌──────────────── 主播、标题、分区、关注、通知、分享 ────────────────┐
│                                          │ 聊天 / SC / 榜单 / 粉丝团 │
│                                          │                       │
│              直播播放器                  │     当前标签内容      │
│                                          │                       │
│       清晰度 · 线路 · 音量 · 全屏         │ 勋章 · 表情 · 弹幕输入 │
├──────────────────────────────────────────┤                       │
│ 礼物 / 背包  [常用礼物]  数量  总价  发送 │                       │
│ 当前粉丝身份 · 亲密度 · 任务 · 大航海     │                       │
├──────────────────────────────────────────┴───────────────────────┤
│ 主播公告 / 简介 / 当前活动（按房间提供的内容显示）                 │
└──────────────────────────────────────────────────────────────────┘
```

具体要求：

- **礼物区**：常用礼物横排，其余放弹出面板；“礼物”和“背包”分标签。清楚显示选中项、数量、实际总价、来源及接收主播。可查看礼物说明与当前折扣，不复用过期价格。
- **粉丝团面板**：展示当前房间的自己的勋章、佩戴状态、是否点亮、亲密度与任务；“我的全部勋章”作为独立管理入口。对“加入”“佩戴”“点亮”使用不同按钮和文案。
- **聊天区**：普通弹幕、送礼、入场、系统通知可分开筛选；礼物连送合并，SC 保留专属标签和明确的剩余展示时间。
- **全屏**：保留紧凑弹幕输入和礼物/粉丝团按钮，点开侧边抽屉；不强制把所有营销动画铺满画面。
- **窄窗口与移动端**：折叠侧栏，面板改为底部抽屉；不照搬宽屏三栏。避免虚拟键盘覆盖价格、确认或发送状态。
- **长期观看体验**：记住侧栏宽度、标签与显示偏好；支持键盘焦点、字号缩放和减少动画。菜单打开、刷新榜单或送礼结果更新，不应导致播放器重建或重新连接。

### 界面增强开关与状态约束

| ID | 需求 | 验收标准 |
| --- | --- | --- |

| LIVE-UI-03 | 开启时使用增强布局 | 只显示已经适配的模块；游客、无权限、房间不支持等状态有对应说明 |
| LIVE-UI-04 | 界面与网络设置独立 | 改此开关不改变点播并发、直播 CDN、清晰度或未来直播加速设置 |
| LIVE-UI-05 | 播放中即时切换界面 | 不销毁播放器、不重新拉流，不丢音量/清晰度/基础弹幕连接；反复切换无重复监听 |
| LIVE-UI-06 | 保存与恢复偏好 | 重启保留用户选择，合法备份显式值可恢复；缺省值不迁移为开启 |

| LIVE-UI-08 | 原有正确性修复独立生效 | SC 删除、过期和基础重连等修复不因关闭增强界面而被撤销 |
| LIVE-UI-09 | 弹幕输入留在聊天区 | 增强开启后在聊天列表下方直接编辑，不弹到整个应用底部；验证登录发送/回执、输入法、表情/@ 与宽窄窗/全屏；关闭增强时沿用原布局 |
| LIVE-UI-10 | 礼物及粉丝入口移到视频下方 | 增强开启后，礼物、粉丝团/灯牌有独立可识别图标，位于画面下方控制区，宽窄窗与全屏可达；打开面板不重建播放器，交易仍需确认与服务端核对 |

开关仅选择新的观看界面与可用功能入口，不授予账号权益，不替代用户对具体赠礼、入团或续订的操作确认，也不自动执行这些行为。新模块请求按需加载，让正在起播或播放的媒体优先获得资源。关闭后取消非必要后台任务；每个任务按账号、房间和当前开关状态判断结果是否仍有效，避免旧请求把新界面重新打开。

官方前端证据还表明：点亮入口涉及 `sendRelationFansGift` / `sendGiftDirect` 的送礼链路，不能以本地切换勋章图标替代；是否消耗金额依实际礼物和权益核验。佩戴/摘下是另一组操作，界面增强开关不自动触发任一流程。

## 5. 第一优先级：礼物与粉丝团形成完整流程

### 礼物

1. 读取房间当前礼物目录、账号权益与余额；背包单独读取数量、期限和限制。普通面板礼物与背包道具并不是同一来源，发送时不能混淆。[官方道具系统说明](https://link.bilibili.com/p/help/index#/gift-system)
2. 支持选择礼物、数量和接收对象；展示服务端给出的实际价格/折扣/总价。对语聊、多主播房间，必须有明确的接收对象，不能只依赖页面标题。
3. 发送前展示确认信息；连送必须由用户明确开启，停止动作应立即生效。
4. 发送状态至少分为：待确认、提交中、成功、明确失败、结果待核实。收到响应不完整或网络超时时，**不得盲目自动重发付费请求**。
5. 根据平台支持情况使用订单号/请求标识去重，并查询交易、背包与余额进行核对；如果平台没有可用的结果查询方式，保持“待核实”并提供官方记录入口。
6. 公共赠礼消息与自己的发送回执可能先后抵达：不能因此显示两次、扣两次数量，或把公共广播当作唯一付款凭据。
7. 充值先接入官方可用的支付流程；完成返回后刷新余额与订单结果。后续是否做原生支付入口，需要另行确认平台、接口和渠道支持。

### 粉丝团与勋章

1. 房间级身份与账号全部勋章分开：支持查看、切换佩戴、摘下、跳转对应房间。
2. 入团流程根据当前房间能力提供；显示当前费用和操作结果。灯牌礼物、入团支付和普通勋章佩戴不能合成一个含义模糊的开关。
3. 任务展示实际条件、当前进度、可获得奖励、完成/领取状态；点亮与升级都由服务端结果驱动。
4. 仅记录真实观看和用户实际互动；不把打开页面、弹幕连接心跳或本地计时器自动视作完成任务。
5. 退出粉丝团等会影响历史进度的操作单独确认，并明确结果；默认页面不放易误触的删除按钮。

## 6. 第二优先级：SC、大航海与消息完整性

### SC

先补齐接收端删除、过期、重连同步与各视图一致性，再增加购买/发送。价格档位、字数限制、显示时长、房间是否允许和账号是否能发送应来自实时能力。

官方说明明确存在审核过程，而且价格档位与字数可能因房间而异；发送成功后不能直接修改或撤回。因此 UI 需要预览、确认、待审核、发送成功/失败和删除后状态，不能把“付款请求返回”立即等同于“成功显示”。[官方醒目留言说明](https://live.bilibili.com/blackboard/live-superchat-intro-web.html)

### 大航海

补房间内舰队列表、自己的身份/有效期/权益、开通和续费入口，并明确一次性购买与自动续订的区别。自动续订的状态、管理和取消入口不能缺失。官方已有舰长、提督、总督和个人中心管理流程，但具体价格和权益仍应动态读取。[官方大航海帮助](https://link.bilibili.com/p/help/index#/great-navigation)

### 房间消息与权限

用统一的房间状态模型接收弹幕、SC、礼物、连送、身份变更、上下播、禁言、房间公告和互动事件。对未知事件安全忽略并留下不含账号敏感内容的诊断信息；断线重连后刷新必要快照，处理重复、乱序和消息缺口。

发送权限检查应覆盖登录、当前账号、当前房间、禁言/冷却以及权益要求。当前房间或账号切换时，旧面板与旧请求结果不得作用到新房间。价格、库存与权限改变时，应重新确认本次操作，而不是继续使用打开面板时的旧数据。

| 特殊内容与播放 | 房间限定播放器/多视角/赛事专属面板/回放等观看能力 | 需按现行产品及样本确认，不能概括为所有房间都有 |

每一项最终应标为“原生可用”“经验证的内嵌官方面板”“跳转官方页面”“当前平台不支持”或“待确认”，并标明限制原因与复核日期。官方页面过渡入口是实用的阶段性方案，但**不能算作原生功能已等量实现**。

## 8. 建议按完成标准分期

| 阶段 | 主要交付 | 进入下一阶段前的标准 |
|---|---|---|
| L0：官方模块采集与基准 | 爬取官方公开页面及其实际加载的模块资源，记录接口线索和验证级别；记录官方网页和最新官方 PC 版本；准备普通、虚拟主播、SC、粉丝团、大航海、PK、语聊多麦位、活动的代表房间；形成逐项差距表 | 每个对齐项目有入口、账号条件、是否可用、证据与待确认项 |
| L1：默认关闭的开关与基础 | 增强开关默认关闭，保留原布局且与网络设置独立；自适应侧栏、直接输入、公告/身份入口；统一状态；SC 删除/过期同步；基础断线恢复 | 面板与播放器独立；窗口/全屏切换不丢房间状态；消息去重与同步可验证 |
| L2：礼物与粉丝团 | 礼物/背包、普通与付费发送、状态核对；勋章管理、入团、点亮/亲密度任务 | 用户从选择到确认结果的流程完整；网络超时不会引发重复消费；官方页面可核对状态 |
| L3：SC 与大航海 | SC 购买/审核/回执；大航海身份、开通续费与续订管理 | 显示价格与实际结果一致；权限错误、审核、过期和续订状态均可解释 |
| L4：高级观看端对齐 | PK、多人、活动抽奖、装扮、通知消息等逐模块完善 | 按 L0 的逐项矩阵验收，明确各平台仍存在的差异 |

建议先解决视频初始载入的问题，再推进 L1/L2；直播改造应作为独立功能分支设计，避免将播放传输改动和付费互动集中进同一个难以验证的版本。

## 9. 验收口径

- **开关**：默认关闭、开启、再次关闭、重启、旧版升级、合法/缺失/异常备份值分别验证；与点播并发开关组成四种组合，不互相改值；播放中切换不重新拉流，后台任务不重复，已提交结果不丢失。
- **界面**：桌面正常窗口、窄窗口、全屏、画中画、大字号下，核心信息不截断；礼物总价与接收人清晰；键盘操作不会误发礼物；弹窗不触发播放器重建。
- **覆盖矩阵**：房间类型至少含普通、虚拟主播、语聊多麦位、PK、活动；账号角色至少含游客、普通已登录、粉丝团成员、大航海成员，以及具备房管权限的测试角色；播放模式至少含普通窗口、全屏、画中画、仅音频。按实际可获得样本记录未测项。
- **真实行为**：以账号在官方页面看到的持有、佩戴、点亮、亲密度、背包和交易状态为核对依据。为测试准备明确授权的账号与支付样本；本次没有进行任何实付测试。
- **网络异常**：覆盖提交前断网、提交后超时、响应重复、消息先到/后到、重连、账号退出、切换房间。结果未知不得显示为失败后自动再扣费。
- **消息正确性**：SC 删除/到期在列表与全屏一致；礼物连送不重复计数；换房后不残留旧房消息和身份；未知协议字段不导致播放崩溃。
- **性能**：礼物动画关闭时无额外渲染；高消息量下有队列上限、合并和虚拟列表；记录互动面板打开前后的播放器掉帧、CPU、内存、网络变化。具体性能阈值先测基线再约定。
- **接口稳定性**：服务端返回价格、权益、活动能力与任务定义为准；区分未登录、未开通、无权限、房间不支持、接口不可用。任何原生能力暂不可用时，应给出可操作的官方入口及明确状态。
- **完成度**：报告不能只写“已支持直播礼物”；必须逐项列出实现、已测、未测、官方跳转、平台限制。最新官方 PC 客户端未实测之前，不宣称已完成完全对齐。
